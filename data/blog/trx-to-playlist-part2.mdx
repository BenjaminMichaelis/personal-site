# From TRX to Playlist: Building a Dev-Friendly Test Toolchain

## Part 2: Parsing the Playlist and TRX Files – Lessons from the Trenches

In [Part 1](./convert-trx-to-vs-playlist) I shared why I built a TRX → VS playlist converter. This post is the how: how I parse both formats, what tripped me up, and the practical choices I made.

---

## Discovering V1 vs V2 Playlist Formats

I started assuming “a playlist is a playlist.” It isn’t. Visual Studio uses two formats:

- **V1:** Straightforward XML; just fully qualified test names.  
  Example:
  ```xml
  <Playlist Version="1.0">
      <Add Test="Namespace.Class.Method" />
  </Playlist>
  ```
- **V2:** More expressive; supports rules/conditions in addition to names.  
  Example:
  ```xml
  <Playlist Version="2.0">
      <Rule type="Test" match="Namespace.Class.Method" />
      <!-- ... -->
  </Playlist>
  ```

Visual Studio tends to produce V2 now, but plenty of tools (and older workflows) still use V1, and V1 is simpler to generate. I support both and detect the version up front.

To understand the shape of things I peeked at `Microsoft.VisualStudio.TestWindow.Core.dll` with DNSpy, then built small models for each version.

## Using AI Tools and Failing Tests to Guide Development

I scaffolded the solution with my [NuGet template](https://www.nuget.org/packages/BenjaminMichaelis.Dotnet.Templates):

```bash
dotnet new install BenjaminMichaelis.Dotnet.Templates
dotnet new bmichaelis.nuget
```

I leaned on GitHub Copilot and Claude to sketch out models from the XML. Helpful, but occasionally wrong. The thing that kept me honest was tests. Writing a failing test first made the direction clear and caught subtle parsing bugs early. I focused on tests that:

- Parse real-world playlist files (V1 and V2)
- Round-trip (parse, then re-serialize, then diff against the original)
- Handle unusual edge cases and metadata

I also grabbed real `.playlist` files from GitHub to expand coverage, since the VS UI doesn’t make V1 files anymore.

## Building VSTestPlaylistTools.\* and TrxLib

Out of this fell a handful of small, focused packages:

- [VSTestPlaylistTools.V1Playlist](https://www.nuget.org/packages/VSTestPlaylistTools.V1Playlist)
- [VSTestPlaylistTools.V2Playlist](https://www.nuget.org/packages/VSTestPlaylistTools.V2Playlist)
- [VSTestPlaylistTools](https://www.nuget.org/packages/VSTestPlaylistTools) (utility for format detection)
- [TrxLib](https://www.nuget.org/packages/TrxLib) (my take on a robust, extensible TRX parser)

A quick lesson learned: don’t assume existing libraries cover your edge cases. I tried [jonsequitur/t-rex](https://github.com/jonsequitur/t-rex) first; it’s good, but it missed some tricky cases around how test and class names are embedded. I ended up writing my own parser that supports the full TRX schema and exposes both a friendly model and a “raw XML escape hatch” when needed.

Sample:

```csharp
using TrxLib;
var results = TrxParser.ParseFromFile("results.trx");
foreach (var test in results.Tests)
    Console.WriteLine(test.FullyQualifiedName);
```

## Handling Format Quirks and Ensuring Fidelity

One big gotcha: Visual Studio expects **fully qualified test names** in playlists. Some TRX files only give the method name or separate class + method.

Older TRX:

```xml
<TestMethod className="Namespace.Class" name="MethodName" />
```

Newer TRX:

```xml
<TestMethod className="Namespace.Class.SubClass" name="MethodName" />
```

Playlist expects:
`Namespace.Class.MethodName`

So I stitch them together when needed:

```csharp
var fqName = $"{test.ClassName}.{test.MethodName}";
```

I also aimed for round-trip fidelity: parse → write → diff should be byte-for-byte identical. That’s how I caught small formatting changes early.
